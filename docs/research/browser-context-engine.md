# 旧版浏览器连接上下文到下载引擎

日期：2026-10-18。纯静态分析，不执行 DLL，不恢复真实浏览器连接，不联网。

## 已闭合的路径

```text
浏览器/主程序交接块
  → 00460236：WSASocketW重建连接，接收协议块与已读缓存
  → 0045d187：按任务对象字段提取协议块/缓存，建立命令并入队
  → 0045cb9a → 004766d2：复制命令参数
  → 00476af8（间接CALL指令00476b08）
  → DAT_004c9bc0 = set_addition_info
  → download_engine.dll!1000b67e
  → 查询附加信息接口10370fd8
  → 接口虚表+0x0c
  → 主任务代理10081ac8
  → 代理内部对象的等值接口103701ac
  → 内部接口虚表+0x0c（最终消费者尚未可靠确定）
```

主程序来源证据见 `analysis/exports/minithunder-browser-receiver/{00460236.c,0045d187.c,0045cb9a.c,004766d2.c}` 与 `analysis/exports/minithunder-context-refs.txt`；引擎证据见 `analysis/exports/minithunder-engine-ghidra/pseudocode/{1000b67e.c,1000a861.c,100805ee.c,10081ac8.c}`、seed-references.jsonl。

主程序00460236把WSASocketW重建值存任务+0x2c8，0x274字节协议块存+0x2dc；缓存对象+0x2cc，当前数据起点+0x2d0，终点+0x2d4。0045d187在存在协议块时，把协议块、缓存起点、终点减起点的长度交给命令创建器。

004766d2复制0x274字节协议块到命令+0x1c；复制缓存至命令+0x20，分配len+1且追加NUL；命令+0x24为len。00476af8原指令读取这三字段并压栈，经00476b08调用绑定槽位。因此实际附参顺序已确定为：

```text
set_addition_info(taskHandle, protocolInfoPtr, recvDataPtr, recvLength)
```

**不能按名字把它猜成 `(task, buffer, length, extra)`。** 三个附参里前两项都是指针，最后一项才是长度。这也是仅看Ghidra参数名容易误判的实例。

## 引擎入口：1000b67e

导出先用100063f6确认任务句柄在注册集合中；无效返回-12。protocolInfoPtr或recvDataPtr为零时返回-11；随后1000a861通过任务QueryInterface请求标识10370fd8；若接口不存在，返回0x80004002。

接口存在时，以原顺序调用接口虚表+0x0c：`(interface, protocolInfoPtr, recvDataPtr, recvLength)`。这个导出将默认返回值设为0，**没有保存被调用方法的返回结果**，所以“set_addition_info返回0”只能证明到达转发路径，不能证明内部成功接管了socket、正确消费缓存或没有丢数据。

主程序00476af8把此导出返回值等于0转换为true，因此上层同样会失去更深层的失败信息。新版应使请求接收、接管成功、下载开始分别有明确确认，不能沿用这个宽松判据。

## 任务代理与等值接口

100805ee是任务代理QueryInterface：当标识等于10370fd8时，返回主任务接口指针+0x64的子接口（注意这是相对主接口，不是完整对象的固定偏移）。对应虚表10379ce4，+0x0c指向10081ac8。虚表第0项是调整this后跳入100805ee的thunk100814b5，字节表证据可直接核对。

10081ac8取传入接口对象+4所指向的内部对象，请求103701ac接口；缺失时返回0x80004001（未实现），否则仍原序转发三附参到+0x0c，并返回内部结果。**这个内部结果在导出1000b67e处被丢弃。**

103701ac与10370fd8在样本内的16字节标识完全相等（两份常量），所以这两次查询是同一接口的代理转发，不是两个无关接口的名称联想。可由PE字节定位复核：103701ac文件偏移0x36f5ac，10370fd8文件偏移0x3703d8。

## 当前仍未知

更新：后续已定位普通任务的附加信息接口实现 `100aded0`、消息 `0x78` 分发、数据二次复制和预读 HTTP 头识别。下面第1项的缺口已缩小，详见 browser-context-consumer.md；实际 socket 恢复和传输闭环仍未验证。

1. 代理内部对象的具体运行时类型取决于普通下载构造分支；最终+0x0c消费者未闭合到可审计函数体。
2. 最终消费者是否再次WSASocketW、使用主程序已重建socket、或仅使用协议块/缓存的一部分，尚无可靠静态证据。不能宣称socket实际复用已完整验证。
3. 协议块含有效Winsock协议信息，但未恢复整个私有包格式、所有权和关闭时机；recvLength为零时的接管语义也未确定。
4. 本路径是否只为特定IE下载类型触发、HTTPS/socket TLS状态是否可跨进程继续、失败如何回退，仍需对应条件及隔离动态实验。

没有为了补图而把另一处包含同GUID比较但未有可靠函数边界的代码强行认定为最终实现。引擎已有图仍是静态候选/代理图，不是完整运行期对象图。

## 对现代浏览器集成的限制

旧版路径明确携带协议块和预读字节，超出了普通URL粘贴。现代公开downloads API与Native Messaging只提供受限的下载元数据及JSON通信，不能凭此获得浏览器的已连接socket或TLS会话。新版应按 browser-capture-modern.md 的可重放GET接管、登录上下文传递与明确回退设计；不得承诺复刻旧版连接级无损移交。
