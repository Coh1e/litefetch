# `core-bt` 偶发失败：观察与处置

日期：2026-10-29。今天两次整套运行里 `core-bt` 失败过两次，两条不同的断言：

```
bt: FAIL: seeder listens on a loopback port            (5.9 s)
bt: FAIL: a second peer downloaded the torrent from us  (52.7 s)
```

两次都单跑通过，整套重跑也通过。

## 观察

- 第一类：`listen_port` 还没报到就断言，早前已改成有界轮询（100×50 ms）；
- 第二类：本地一喂一的 P2P 传输在**整套负载下**没在 30 秒内完成。测试本身有 30 秒上限、每 500 ms 轮询一次。

## 处置（只改真实缺陷，不改断言）

`listenPort` 是 `std::int32_t`，由播种线程写、测试线程读——**数据竞争（UB）**。已改为 `std::atomic<std::int32_t>`，
读写都走原子操作。这可能正是"偶尔读到 0 或陈旧值，于是连了个错误端口"的来源。

改完连跑三次 `core-bt`：13.1 s、13.1 s、14.4 s，全部通过；整套 165.2 s 全绿。

## 没有做的事

- **没有延长超时**来让它更容易通过；
- **没有加重试**掩盖失败；
- **没有删断言**。

## 如果再次偶发

下一步不是继续放宽，而是：
1. 记录当次 `listenPort`、播种/下载的 `total_wanted` 与 `total_wanted_done`；
2. 判断是"端口未就绪"还是"传输真的慢"，再决定是改测试就绪判据还是查产品侧。

本机不是干净环境，整套跑时同时有 CMake、ninja、浏览器探针历史进程的干扰，这类时序问题在
`#28` 的干净机器上应重新观察。
