# 浏览器接管附加信息：普通任务实现与后台消息

日期：2026-10-18。使用既有 Ghidra 数据库，只做静态读取和反编译；没有加载或运行迅雷组件，也没有改浏览器配置。

样本：download_engine.dll，SHA-256 `38dd7f676a592bf1810e314e370b28fa4a43e2df3e6a8181447335333d1b0083`。导出脚本在读取前核对数据库记录的样本哈希。原始文件另行计算哈希核对。

## 已定位的具体实现

此前停在 `10081ac8` 对内部对象同一 GUID 接口的查询。此次找到另一处 GUID 比较的指令链：

1. `100ae8e0` 开始的查询逻辑在 `100aeb58` 比较 `10370fd8`，匹配分支 `100aeb6d` 返回对象 `+0xb4`。
2. `100ae660` 的构造伪代码把 `1037c7e4` 写入对象 `+0xb4`，并使用字符串 `CP2spTask_NEW`。`1007f563` 创建此对象并查询普通任务接口，来源字符串包含 P2spTaskShell.cpp。
3. 该虚表前三项为调整 this 后查询/引用计数的 thunk，第四项 `1037c7f0` 的实际指针为 `100aded0`。这不是仅根据 GUID 名称猜测的方法。
4. 新建、继续和另一个构造路径均可见相同的虚表赋值；不据此推断所有运行时类型都走此分支。

因此普通任务分支已找到可审计的附加信息实现。运行时对象身份和所有分支仍需要动态验证。

## 方法没有同步完成网络接管

`100aded0(interface, protocolInfo, recvData, recvLength)`：

- 分配 `0x27c` 字节消息对象，把协议块复制 `0x9d` 个 DWORD，即 `0x274` 字节。
- 长度大于零时单独分配并复制预读数据；消息 `+0x274` 保存数据指针，`+0x278` 保存长度。长度小于等于零时这两项置零。
- 从接口相对偏移 `+0x78` 取得后台对象，再取其 `+8` 字段作为分发参数；经全局分发接口虚表 `+0x2c` 提交消息号 `0x78`。
- 随后 `XOR EAX,EAX; RET 0x10`，没有根据分发调用的返回值决定成功失败。

这补强了已有判断：`set_addition_info` 返回零不构成下载已经接管成功的证明。这里只能证明到达复制和消息提交路径；内存分配与分发失败语义没有完整恢复。

## 后台处理与释放

`100ceda0` 构造后台对象，字符串为 `p2s_task_event_handler`，主虚表 `1037f8f4`。其 `+4` 项为 `100d4120`，`+8` 项为 `100d49f0`。两处没有既有函数边界，本轮保留指令证据，没有强制建立函数或把反编译猜测当源码。

分发指令先检查消息号不大于 `0x78`，再用两级跳转表：

- `byte[100d496c + 0x78] = 41`；`DWORD[100d48c0 + 4*41] = 100d4841`。
- `100d4841` 把消息数据传给 `100ca340`。
- `100ca340` 用消息块起点、`+0x274` 指针和 `+0x278` 长度调用 `1007aad0`。
- 清理函数按消息号减2索引；对于 `0x78`，索引表值7，目标 `100d4ad4`。该分支检查并释放 `+0x274` 缓存，再释放消息对象。

跳转表数值由原始 PE 字节和 Ghidra 内存两次核对，导出文件保留了计算结果。尚未独立确认全局分发器的队列实现、线程切换及清理调用时机。

## 再次保存上下文并检查 HTTP 头

`1007aad0` 把协议块再次复制到其 this 对象 `+0x5d0` 指向的新内存。预读数据复制到 `+0x5d4`，额外分配一个字节并追加 NUL，长度保存到 `+0x5d8`；随后调用 `10079d90`。

`10079d90` 查找 `\r\n\r\n`，若找到则把之前的内容作为字符串交给 `10094e30`，再根据 `10093bd0` 的结果给对象 `+0x5dc` 写1或2。这确认了预读内容参与 HTTP 头识别；没有据此把1/2命名为某种已确认状态。

对指令区间 `10030000..10100000` 的直接字段文本引用扫描还找到初始化和析构释放。这是有界检索，只覆盖指令中直接出现 `0x5d0/4/8` 的情况；基址调整、别名、间接参数或其他代码区的访问可能漏掉，不能据此断言字段没有其他消费者。
