## 普通正文管道

`10099840` 把 HTTP 头后的预读正文放在管道 `+0x1e8`，长度在 `+0x1e0/+0x1e4`。这对应 `10099e6f` 反编译中 DWORD 下标 `0x7a` 和 `0x78/0x79`，不是另一份无关缓存。

`10099e6f` 的静态控制流：

1. 若预读长度非零，先经管道 `+0x150` 所指接口的 `+0x14` 方法提交该正文，发送内部通知 `0x11`。
2. 释放预读正文，置零指针和长度。
3. 随后才解读本次异步结果：错误、零字节结束或正数字节。
4. 正数字节通过同一接口 `+0x14` 提交，并更新64位已收字节数；已知剩余长度相应扣减，再决定继续读或结束。

`10099b93` 的终止处理也先提交尚存的预读正文，再处理结束通知。

因此能证明的是“在这些结果处理函数中，预读正文先于新结果提交到下游”。不能把它改写为“网络层一定先耗尽预读数据才发起第一笔 socket read”：读请求可以先发起，而下游提交顺序仍由上述方法维持。下游接口是否同步消费/复制、失败是否传播以及是否真正写盘尚未确认。

`10099dea` 每次仅在 `+0x1ac` 为零时安排读取，默认请求1MiB，按已知剩余长度缩小；将活动标记置1后，调用 `+0x158` 设备接口的 `+4` 方法。回调正常分支清标记，再继续安排读取。

## chunked 管道

预读函数 `100975b9` 把正文放进内部缓冲，`+0x1c8` 为游标，`+0x1cc` 为尾位置。`1009797a` 使用同一对字段解析：

- 状态0找分块长度行，以 `100973fc` 按16进制累加长度，推进越过行结束。
- 状态1提交 `min(缓冲可用量, 当前块剩余量)` 的正文，经下游接口 `+0x60` 输出；更新游标、当前块剩余量和累计正文长度。
- 块结束转状态2，检查接下来的 CRLF，再进入下一块。
- 缓冲不足时进入 `100978f9`，把未消费尾部移到缓冲起点，重置游标，再向设备接口请求补读。活动标记防止在此分支重复提交读取。
- `10097c8e` 的完成结果满足相应状态检查后，把本次字节数计入缓冲，再调用 `10097c22` 继续解析；解析返回2时走错误，返回3时走结束。

这一链支持“现有预读内容和后续网络字节使用同一缓冲继续解析”的结论。零块、trailer、块扩展、超长长度、半行、异常关闭等所有边界没有完成逐项验收；函数返回2/3仅按已见分支标注，不宣称实现完整符合HTTP规范。

## 设备适配层

构造函数 `100bc170` 把设备虚表设置为 `1037de18`。原始 PE 中：

| 设备槽位 | 实现 | 已见行为 |
|---|---|---|
| +4 | `100c5ae0` | 经操作对象 `+0x30` 安排参数后，调用内部调度接口 `+0x0c`，把操作状态写2 |
| +8 | `100bc090` | 类似路径走内部调度接口 `+0x10`，把操作状态写3 |
| +0xc | `100c5b20` | 转发内部接口 `+0x1c` |

这些方法没有既有函数边界，本轮保留原指令，没有根据推测强建函数。状态2与 chunked 回调的状态检查一致，但内部调度接口到 Winsock 的完整读取路径仍待闭合；仅凭名称不把它认定成某一个具体 WSARecv 调用。

## 对新版的具体要求

新版公开浏览器接口不会提供旧版的 socket 和预读缓冲。浏览器扩展负责提交可重放请求；本机必须先持久化接管事务，再明确完成浏览器取消与本机启动，避免任务丢失或重复开始。

旧版的缓冲顺序研究用于理解其连接级接管能力，不能直接替代现代扩展的 prepare/commit、幂等、崩溃恢复与回退验收。后续实现仍使用独立开源组件，不加载迅雷引擎、不接入迅雷加速网络。
